## Tenant isolation trace (LG-001)

`get_batch_detail()` loads batch metadata, derives authorized client IDs from the authenticated user's assignments, and rejects a batch with no authorized client (`apps/api/batches.py:330`). Ad reads then go through `get_batch_ads()`, which returns an empty list for no authorized clients and executes a query constrained by both batch ID and `client_id = ANY(allowed_clients)` (`apps/api/batches.py:106`). This helper is also used by SSE and metrics handlers (`apps/api/sse.py:170,246`, `apps/api/metrics.py:112,621`). No empty-result fallback remains. The isolation tests use an in-memory fake database; they do not access production client data.

## Authentication and modal behavior

The original report's recommendation to remove JWT requirements contradicts the product documents. The API requires an active user token, then applies role checks and assigned-client authorization; invalid or expired tokens fail with 401. A valid authenticated user without the required role is rejected with 403. There is no documented guest session model, and IP is only an additional batch-history filter, not an identity credential. Cross-tenant campaign history is filtered by assigned clients and uploader IP.

The home modal now checks a trimmed prompt or a non-empty selected file before opening. An empty file and missing creative media do not count as valid file input. Existing upload and launch paths remain unchanged. Browser-level behavior remains untested because no frontend test infrastructure is configured.

## Meta integration and safety

### Internal representation and current API path

Launch Gate stores ad rows with `ad_id`, `batch_id`, `client_id`, normalized platform, headline, ad text, destination URL, creative reference, and content hashes. `LaunchBatchRequest.target_platforms` is normalized to Facebook/Instagram and the API loops over each selected destination. Dispatch records are keyed by a deterministic dispatch ID derived from the ad ID, platform, and content hash; a returned `platform_ad_id` is stored in `ad_live_dispatches`. The current schema and code do not model a complete campaign → ad set → creative → ad ID chain.

The discovered Meta creation schemas require a staged workflow: `ads_create_campaign` requires `ad_account_id`, `campaign_name`, `objective`, and `buying_type`; `ads_create_ad_set` requires `ad_account_id`, `campaign_id`, `ad_set_name`, `billing_event`, `optimization_goal`, and `targeting`; `ads_create_creative` requires `ad_account_id`; and `ads_create_ad` requires `ad_account_id`, `ad_set_id`, and `ad_name`. These are writes. `ads_get_ad_accounts` and `ads_get_ad_entities` are reads. No campaign, ad set, or creative creation was attempted.

### Authorization, retries, persistence, and remaining safety gaps

The API's launch endpoint requires a buyer or account-manager role, checks client assignment, and validates the content hash. It then changes a pending approval to `approved` inside the launch endpoint before dispatch (`apps/api/campaign_flow.py:236,381`). The frontend performs preflight before calling launch, but the API does not require a separately persisted successful preflight result or an existing reviewer approval. Whether the launcher's explicit modal submission is sufficient human approval is unclear against the PRD's separate reviewer approval step; decide this before enabling any external dispatch.

The old MCP wrapper called the synthetic platform tool directly and did not discover/validate that tool's remote schema. The lower-level MCP client retries transient tool-call failures; retrying a non-idempotent create operation can duplicate a provider object. Dispatch IDs are stable locally, but no Meta-side idempotency contract is established. Failure responses and confirmed platform IDs are persisted to dispatch/send records; no remote campaign/ad set/creative reconciliation exists. Facebook and Instagram are represented as separate per-platform loop calls, not as Meta placement fields.

This version of Launch Gate is defined to use the stand-in platform and keep live writes locked. Added guards reject Meta writes in both the platform dispatcher and the lower-level MCP client, even if `META_MCP_ENABLE_LIVE` or `META_MCP_ALLOW_WRITES` is later set. All audit tests kept both environment flags disabled; one direct-client test passes `allow_writes=True` only to prove the hard policy refusal and does not perform network I/O.

Read-only remote discovery confirmed the current tool names and property/required-field metadata. The earlier report's ad-account permission finding remains unverified here. The scripts' safe read-only smoke operation is available, but a current account permission check is still needed before any future integration work.
